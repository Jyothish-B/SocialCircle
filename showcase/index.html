    Scoring

    Five factors, one score out of 100

    Every factor is normalised into the range 0 to 1 and the weights sum to 1, so the match score is bounded by construction. Change the weights in the demo and the ranking reorders live.

    Saturating, not min-max

    Min-max normalisation depends on who else made the list, so the same pair would score differently on every request. 1 - e-x is computed per pair: scores stay stable across users, and the tenth mutual friend adds less than the second.

    When a user has no friends at all, the structural factors are zero for everyone, so the engine switches to a cold-start formula built from onboarding signals. Pick Meera in the demo to see it.

    The celebrity problem

    One user with a million friends turns a two-hop expansion into a million rows. Five defences, in the order the queries apply them:

    • implementedDegree-capped expansionEvery hub is checked with COUNT { (m)-[:FRIENDS_WITH]-() } <= 200, which compiles to an O(1) getDegree lookup.
    • implementedAdamic-Adar down-weights hubsA mutual friend contributes 1 / ln(degree), so skipping celebrities costs almost no accuracy.
    • implementedBounded branchesCity and activity branches stop at LIMIT 50, so a metro of ten million cannot flood Stage 1.
    • modelledSeparate relationship typesFollower edges to public figures belong on :FOLLOWS, which friendship traversals never touch.
    • batchPrecompute offlineFor extreme hubs, GDS writes SIMILAR_TO overnight and the online path serves it in O(k).
    Data model

    Attributes are nodes, signals live on edges

    Interests, places, schools and employers are nodes, so "who else likes Hiking" is a traversal, not a scan. Friendship is stored once and matched in both directions. Properties marked GDS are written by the nightly batch job.

    Project defense

    Four decisions worth defending

    Each one comes with the cost it pays. Examiners ask about the trade-off more often than the feature.

    Two-stage retrieval on index-free adjacency

    Bounded multi-source candidate generation, then scoring on a small set: 14 candidates for Jyothish. Each hop follows stored pointers, so cost tracks the edges touched, not total users. SQL would self-join a friendships table once per hop.

    Trade-offThe hub cap trades recall for predictable latency. Two people linked only through a celebrity are never suggested, which is usually right because that link is weak evidence.

    Weighted Adamic-Adar with a saturating transform

    Each mutual friend votes 1 / ln(degree), scaled by both tie strengths. Plain counts reward people who know everyone and Jaccard penalises active users. Adamic-Adar is among the strongest classic link predictors (Liben-Nowell and Kleinberg, 2007).

    Trade-offCost grows with the two-hop neighbourhood. The saturation constant 1.5 is a hyperparameter, but it buys scores that are stable per pair instead of relative to each result list.

    Online query, offline GDS, graceful degradation

    Louvain, FastRP and kNN run as a batch job and write properties the online query reads with coalesce. FastRP runs on users and their attributes together, so a friendless user still gets an embedding.

    Trade-offFreshness against latency. Batch outputs are hours old, which is why the cold-start query computes attribute similarity live instead of waiting for the next run.

    Cold-start ladder with diversity re-ranking

    The formula switches by available data: interests, then group or employer, then city, then active users. At most two people per Louvain community, and every result carries a reason and a factor breakdown.

    Trade-offThe diversity cap gives up some precision at k for coverage, which matters most when you know nothing about the user. Explanations are free because they reuse the scored features.

    Likely questions
    Why not just count mutual friends?

    Kavya and Rahul both share two mutual friends with Jyothish. Tie strength, freshness, interests and distance separate them: 58.5 against 51.9. Open "Why" on either result in the demo to see where the gap comes from.

    How do you know the weights are right?

    They are priors, not learned values. To tune them, hide 10% of friendship edges, run the recommender, and measure precision and recall at 10. The next step is logistic regression on accepted and ignored suggestions, using these five factors as features.

    What happens if GDS is not installed?

    Everything except the batch script still runs. The community and embedding terms evaluate to zero and the other four factors carry the ranking, which is exactly what the demo shows with the Louvain switch off.

    Directed or undirected friendship?

    Neo4j relationships always have a direction, so each friendship is stored once and matched with -[:FRIENDS_WITH]-. The backend uses an undirected MERGE so a reverse duplicate can never be created, and GDS projects it as UNDIRECTED.
